# Media plan: photos, music, video

Status: plan for review. Nothing here is built. It follows the same approach as `docs/RSVP_PLAN.md`: decide first,
build in small steps. It replaces the "Supabase Storage" line for media in `docs/TECHNICAL_ARCHITECTURE_DECISION.md`.

The service limits quoted here come from search results, because the providers' own documentation could not be
opened from the development environment. **Check each figure in the Cloudflare and Supabase dashboards before relying
on it.**

## Decisions

| # | Question | Decision |
|---|---|---|
| 1 | Where the files live | **Cloudflare R2.** Supabase keeps only the details about each photo. |
| 2 | Photos per wedding | **12** *(suggested, to confirm)*. Enough for the largest design (3 named spots plus a gallery). |
| 3 | Music | **A built-in library of short tracks**, served as static files. No uploads in the first version *(suggested)*. |
| 4 | Video | **Not hosted.** A later paid option, or a link to a video site *(suggested)* |
| 5 | Image processing | **In the guest's own browser before upload**, never on the server (see "Why not on the server"). |

## Where things stand today

- No photos are stored. The editor says "Photo uploads unlock when photo storage is available".
- The server refuses any embedded image data (`data:` addresses) in an invitation, and the public page returns no
  photo addresses.
- A `wedding_photos` table already exists (storage path, alt text, size, order) with no rows and no storage behind it.
- The server limits a gallery to 4 photos. The designs need more: Cinematic has 3 photo spots plus a gallery, Fairy
  Tale 1 plus a gallery.
- The design artwork shipped with the site is about 3 MB in 219 files, served free by Cloudflare Pages. It stays there.

## How it works

### Upload
1. The couple chooses a photo in the editor. The browser reads it, fixes its rotation, **re-draws it on a canvas
   and re-encodes it**. That strips location and camera details (EXIF), which matters for privacy.
2. It makes two sizes: a **full** picture (long edge 1600 px, about 200 to 300 KB) and a **thumbnail** (480 px, about
   30 to 50 KB). WebP when the browser can write it, JPEG otherwise.
3. The browser sends both to `POST /api/weddings/:id/media` with the couple's edit token. The server (a Cloudflare
   Pages Function) checks everything below, writes them to R2 through a bucket binding, and records a row in
   `wedding_photos`.

### Server checks (strict, because anyone with an edit link can call this)
- Edit token valid for this wedding.
- File is WebP or JPEG by its first bytes (not by the name or the type the browser claims).
- Full picture at most 600 KB, thumbnail at most 100 KB. Anything bigger is refused.
- At most 12 photos per wedding and 8 MB in total per wedding.
- Upload rate limit with the same hourly counter used for RSVP (`rsvp_rate_hit`, generalised): 60 per hour per
  device per wedding.
- File names are generated by the server (`w/<wedding id>/<photo id>-full.webp`), never taken from the browser.

### Showing photos
- Photos are served from a **media address on a domain you own on Cloudflare**, for example
  `media.yourdomain.com`, connected to the bucket. Cloudflare then caches them, so repeat views cost nothing.
- The default `r2.dev` address is meant for testing and is rate limited, so it is not used in production.
- The page's security rules (`_headers` and `functions/_shared/security.js`) allow images from that one address.
- The public invitation data gains photo addresses (thumbnail and full) and size, but still no internal paths.
- Pages load **thumbnails first** and the full picture only when a guest opens one.
- **If there is no domain yet:** a fallback is to serve photos through a Pages Function with caching. It works, but
  every photo request then uses one of the free daily Function requests, so it does not scale as far.

### Deleting
- Deleting a photo, or a wedding, deletes its R2 files (everything under `w/<wedding id>/`).
- The 2-month deletion job (RSVP phase 4) also deletes the media. Orphaned files (a failed upload with no row) are
  swept by the same job.

## Why not on the server
A Pages Function on the free plan has a very small processor-time allowance per request. Resizing an image there
would fail or need a paid plan. Resizing in the browser is free, faster for the couple (they upload 300 KB, not
6 MB from a phone), and keeps bandwidth low for guests.

## Why R2 and not Supabase Storage
Search results give these free allowances (confirm in the dashboards):

| | Supabase Storage (free) | R2 (free) |
|---|---|---|
| Storage | 1 GB | 10 GB |
| Bandwidth out | 5 GB plus 5 GB cached | No charge |
| Reads | no separate limit | 10 million per month |
| Writes | no separate limit | 1 million per month |
| Resizing | not on the free plan | not needed (done in the browser) |

Assuming 10 photos per wedding at about 300 KB (both sizes), so **about 3 MB per wedding**:

- **Storage:** about 330 weddings in Supabase, about 3,300 in R2, at the same time.
- **Bandwidth:** one wedding sent to 300 guests who each open it 3 times is about 900 views, about 0.6 GB with
  thumbnails first. Supabase's free bandwidth covers only about 8 to 16 such weddings a month. R2 charges nothing.
- **R2 reads:** 900 views of 10 thumbnails is 9,000 reads per wedding without any caching, so about 1,000 weddings a
  month before caching, and far more with it.
- **R2 writes:** about 20 per wedding, so no concern.
- **Functions:** a public page view uses about 2 of the roughly 100,000 free daily requests (the page and its data).
  Photos from the media address use none.

Because weddings are deleted 2 months after the date, stored media stays bounded instead of growing for ever.

## Data

`wedding_photos` (exists) gains columns: `kind` (spot name or "gallery" or "intro"), `full_key`, `thumb_key`,
`full_bytes`, `thumb_bytes`, `format`. Its row-level rules stay (service key only). The old `storage_path` column is
kept and holds the full picture's key.

The invitation data stores, per photo: id, kind, alt text, width, height, order. Addresses are built from the media
address and the keys, so moving to another domain later changes one setting.

## Privacy and abuse

- Picture addresses are long random keys: unguessable, but anyone who has one can open it. This is the price of free
  caching. It also means a draft's photo can be opened by anyone given its exact address.
- EXIF is removed by the re-encoding. A test uploads a photo with location data and checks the stored file has none.
- Media addresses can be used by others as free image hosting, so keys are random, sizes are capped, and a wedding's
  total is capped. A report-abuse contact goes on the public page footer before launch.
- No face or content scanning is possible on free plans. State this in the terms.

## Music and video

- **Music:** 8 to 12 short loops chosen for weddings, each under 1 MB, in `assets/music/`. Served by Pages, whose
  bandwidth is free. The couple picks one in the editor; nothing is uploaded. Music never starts on its own (browsers
  block it, and guests dislike it): a visible play button.
- **Video:** not hosted. Later options, each needing a decision: a link to YouTube or Vimeo (needs `frame-src` in the
  security rules), or hosted video as a paid package. Cloudflare Stream is paid, and R2 egress is free but video files
  are large, so it needs a size cap and a paid tier.

## Order of work

1. **Photo upload and display.** Browser resizing, upload endpoint, R2 binding, `wedding_photos` columns, editor upload
   (add, replace, remove, reorder, alt text), designs get real photos, public page shows them. Migration plus tests.
2. **Limits and housekeeping.** Usage line in the editor ("7 of 12 photos"), orphan sweep, delete with wedding. Joins the
   RSVP retention job.
3. **Intro image** (same pipeline).
4. **Music library.**
5. **Video**, only after a decision.

Each step ships with tests: the strict server checks (wrong type, too big, too many, no token, wrong wedding), EXIF
removal, public data shows no internal keys, deletion removes files, and a browser test of the upload flow with the
upload address stubbed (nothing touches production).

## What you need to do (outside the code)

1. Create an R2 bucket (for example `invitestudio-media`) and bind it to the Pages project as `MEDIA`.
2. Connect a media address (a domain you own on Cloudflare) to the bucket.
3. Run the new Supabase migration when it is ready.
